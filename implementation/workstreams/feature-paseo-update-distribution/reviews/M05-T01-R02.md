## Finding

R01's process-local race is corrected, but its required topology constraint is not durably enforced or proved.

The corrected writer holds an exclusive `fcntl.flock` around the authoritative digest read-check-write-readback sequence. The new contention test correctly proves that two processes sharing the same lock file serialize and that the loser re-reads the winner digest and fails before mutation.

However, the default lock is created under the executing host's `tempfile.gettempdir()`. That lock cannot serialize writers running on different hosts or in isolated filesystems. R01 explicitly allowed a host-local primitive only if the writer topology was constrained and proved so competing writers could not exist outside that lock domain. The new execution evidence states that production is a single Tower-side writer domain, but M05-T01 adds no durable mechanism that enforces that statement: the script itself has no Tower/domain admission check, shared external lock, lease/CAS, or equivalent boundary. Given valid gate/guard inputs and registry credentials, another invocation outside Tower's local lock domain can still enter the same read-check-write race against the Tower writer.

Therefore the exact Card acceptance — a project-owned serialized single-writer promotion path with stale/newer candidates failing closed — is not yet established for the allowed production mutation surface, and PUD-REQ-019's serialized accepted channel remains unproven.

- enforce a durable Tower-only promotion admission boundary such that every production `:accepted` mutation through this project-owned path must execute inside the same Tower lock domain, and add evidence/tests proving an out-of-domain invocation cannot reach registry mutation; or
- replace/augment the local file lock with a serialization/CAS primitive whose scope covers every host allowed to mutate the accepted alias.

Retain the now-correct in-domain lock coverage and contention test, exact final-gate/armed-guard checks, immutable digest-only rollback identity, immediate registry readback, and the no-production-`:accepted`-movement boundary during M05.
