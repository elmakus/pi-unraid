### F2 — Bundled direct-Meta model data says contributor does NOT support max (official/upstream)

- `dist/providers/data/meta.json` in installed `pi-ai@0.87.1` (file header: auto-generated by
  `scripts/generate-models.ts`, "Do not edit manually"), provider `meta`, `api: openai-responses`,
  `baseUrl: https://api.meta.ai/v1`:
  - `muse-spark-1.3-contributor`: `thinkingLevelMap.max = null` (unsupported).
  - `muse-spark-1.3` (non-contributor): `thinkingLevelMap.max = "max"` (supported).
  - Older entries (`1.1`, `1.2`, `1.2-contributor`): `max = null`.
- Fresh registry pulls of `@earendil-works/pi-ai@1.0.2` (latest) and `@0.99.2` contain the **same**
  mapping (`1.3-contributor` → `max: null`; non-contributor `1.3` → `max: "max"`; key prefix renamed
  to `chat:` in 1.0.2). The `null` is stable upstream, not a transient or a stale pin.
- Official catalog site confirms the pinned position: `https://pi.dev/models/meta/muse-spark-1-3-contributor`
  embeds `thinkingLevelMap: { …, "xhigh": "xhigh", "max": null }` with `baseUrl https://api.meta.ai/v1`.

### F3 — Same artifact contradicts itself across provider paths (official/upstream)

- Bundled `dist/providers/data/openrouter.json` in the **same** `0.87.1` artifact maps
  `meta/muse-spark-1.3-contributor` to `thinkingLevelMap.max = "max"` (and likewise non-contributor
  `1.3`). So one pinned artifact advertises `max` as supported over OpenRouter while marking it
  unsupported on the direct-Meta path for the identical model id.
- Upstream maintainer position on exactly this split (`earendil-works/pi#9658`, comment by
  `davidbrai` 2026-09-18): OpenRouter's API lists `max` in `reasoning.supported_efforts` for this
  model, but direct Meta rejects it — "misconfigured on openrouter's side". The direct-Meta `null`
  is therefore the deliberate upstream-consistent position, not an omission.

### F4 — Harness semantics: unsupported max is silently clamped; wire passes forced values through (official/upstream source)

- `dist/models.js`: `getSupportedThinkingLevels()` excludes any level mapped to `null`; `xhigh`/`max`
  are opt-in (require an explicit non-null entry). For bundled contributor data, supported levels are
  `minimal..xhigh`; `max` is excluded.
- `dist/models.js` `clampThinkingLevel(model, "max")` on bundled contributor data returns `"xhigh"`
  (downward scan). `dist/core/agent-session.js` `setThinkingLevel()` applies that clamp silently.
  Consequence: invoking the fixed `max` profile against **unmodified** pinned data would execute at
  `xhigh` while evidence records `max` — a fake-`max` hazard for final-validation evidence.
- `dist/api/openai-responses.js` wire serializer maps effort as
  `model.thinkingLevelMap?.[effort] ?? effort`: a *forced* `max` is passed through verbatim as
  `reasoning.effort = "max"` even when the map entry is `null`. The map therefore gates
  selection/clamping, not the wire — enforcement must live at profile validation, not transport.

### F5 — Local runtime catalog advertises the inverse of the bundle (project/runtime, non-inference)

- `paseo provider models pi --json` (non-inference catalog readback, 2026-10-04):
  - `meta/muse-spark-1.3-contributor` → `thinkingOptionIds: minimal, low, medium, high, xhigh, max`
    (**includes** `max`).
  - `meta/muse-spark-1.3` (non-contributor) → `minimal..xhigh` (**excludes** `max`).
  - All other Muse entries exclude `max`.
- This is exactly inverted relative to bundled `meta.json` (F2). The inversion is explained, not
  mysterious (F6–F7), and catalog presence alone proves nothing about wire acceptance (no inference run).

### F6 — The local max advertisement depends on an unmanaged HOME override (project/runtime)

- `/home/paseo/.pi/agent/models.json` (mtime 2026-09-28, mode 600) contains:
  `{"providers": {"codex-lb": {…}, "meta": {"modelOverrides": {"muse-spark-1.3-contributor": {"thinkingLevelMap": {"max": "max"}}}}}}`.
- Per `docs/models.md`, `modelOverrides` changes metadata for an existing built-in model without
  replacing the provider list — i.e. this single local file is what promotes contributor `max` to
  supported in this environment.
- Provenance gap: **no `modelOverrides`/`thinkingLevelMap` delivery exists in repository source**
  (repo-wide grep finds the strings only in historical evidence and Codex-LB provider specs, never as
  managed Meta/test-policy delivery; `Dockerfile`/`compose.yaml`/`config/`/`scripts/configure-*`
  deliver no `models.json`). The override is environment-local and is **not** part of the reproducible
  candidate/build/provenance chain P4 M07-T04 requires ("frozen, reproducible source/provenance" for
  "image plus any intentionally staged instruction/provider/policy bundle").
- Cached merged view `/home/paseo/.pi/agent/models-store.json` (refreshed 2026-10-04 14:50) shows the
  override in effect: contributor `max → "max"`. It also shows non-contributor `1.3` as `max → null`,
  differing from bundled `meta.json` (`max → "max"`); the provenance of that second flip (dynamic
  catalog refresh vs cache writer) was **not** traced — recorded as an explicit unknown (C4).

## Explicit conflicts

- **C1 (core, unresolved): catalog vs bundle, inverted.** Paseo local catalog: contributor HAS `max`,
  non-contributor 1.3 LACKS it. Bundled `meta.json` (0.87.1 through 1.0.2) + `pi.dev`: contributor
  LACKS `max`, non-contributor 1.3 HAS it. Reconciliation by weight: the local advertisement is fully
  explained by the unmanaged `models.json` override (F6); it is environment observation, not capability
  proof. Effective wire acceptance of `effort: "max"` for contributor on the direct-Meta path remains
  **unproven** (no inference permitted in this obligation) and counter-indicated by C2.
- **C2 (unresolved): same artifact, two answers.** Bundled `openrouter.json` (`max → "max"`) vs bundled
  `meta.json` (`max → null`) for `meta/muse-spark-1.3-contributor`. Maintainer (#9658) attributes the
  `max`-advertisement to the OpenRouter side and reports direct-Meta 400 rejection. `max` support is
  therefore provider-path-dependent; the mandatory test profile uses the direct-Meta path, where primary
  sources say unsupported.
- **C3 (unresolved): practitioner claims both directions.** #10155 reporter: `max` works via opencode
  relay (relay may translate effort values; issue auto-closed by bot, never merit-reviewed; maintainer
  redirects to `anomalyco/models.dev` opencode data). #9658 reporter: `max` → Meta 400,
  `high` works. Different paths; neither transfers to the direct-Meta path. Popularity/claims do not
  override primary source semantics.
- **C4 (unknown): cache flip.** `models-store.json` shows non-contributor 1.3 `max → null`, contradicting
  bundled `meta.json` (`max → "max"`). Refresh provenance untraced; no conclusion drawn.
- **No other material conflict.** Pi version identity is consistent across Dockerfile, shrinkwrap,
  binary, and Paseo diagnostic (all `0.87.1`).

## Limitations

1. No real inference was run (obligation forbids it); effective `max` behavior on any path is observed
   only through metadata, catalogs, and third-party reports — never directly verified.
2. `models-store.json` refresh provenance and Paseo's `thinkingOptionIds` derivation code were not
   inspected; Paseo catalog is treated as observed output of the merged (bundle + override + cache) view.
3. `models.dev` (the generator-upstream the maintainer cites for relay data) returned no usable content
   in this check; relay-path metadata provenance is second-hand via maintainer comments.
4. Upstream issues #9658/#10155 were auto-closed by bot without merit verdicts; only the maintainer
   comments carry weight, and they are supporting, not primary, evidence.
5. Credential availability, provisioning procedure, and provider-side scope restrictions are not
   established (operator-owned per ADR-PUD-004; expected M08 input). No auth material was opened.
6. The Sep-28 origin (author/tooling) of the local `models.json` override was not traced; only its
   content, effect, and absence from repo delivery are established.

## Precise remaining gap (for Main-owned Execution Prep reconciliation, not a decision)

No supported reproducible delivery of **effective** `meta/muse-spark-1.3-contributor` + `max` on the
direct-Meta path exists in the current chain:

- (a) pinned and latest upstream metadata mark the combination unsupported (F2, stable across 0.87.1→1.0.2);
- (b) the only element making it *appear* supported locally is an unmanaged, non-repo-delivered HOME
  override (F6), which P4 M07-T04 provenance requirements do not cover;
- (c) without that override the harness silently executes `max` as `xhigh` (F4), so `max` evidence could
  be recorded without `max` execution;
- (d) with the override the wire would send `effort: "max"`, whose Meta-side acceptance is unproven and
  counter-indicated on the sibling path (C2).

Established without gap: pinned artifact identities + integrity hashes (F1); fixed launcher/policy
request shape (F7); dedicated credential *shapes* as public metadata with values untouched (F8).
Missing-blocker status of profile availability vs credential availability is left to Main: what is
established is that the profile leg currently rests on (b), and the credential leg is unprovisioned by
design until M08.
