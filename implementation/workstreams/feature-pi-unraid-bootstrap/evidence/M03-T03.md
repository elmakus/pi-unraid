## Implemented boundary

Repository-owned deployment now provides the Pi-side Codex-LB client boundary without changing production:

- Compose keeps the accepted Pi home/projects/worktrees layout and adds only:
  - `host.docker.internal:host-gateway`;
  - non-secret `PI_CODEX_LB_BASE_URL` and `PI_CODEX_LB_MODEL` settings;
  - one file-backed Compose secret sourced by `PI_CODEX_LB_SECRET_SOURCE`, defaulting to `/mnt/user/appdata/pi-unraid/secrets/codex-lb.env`;
  - read-only secret target `/run/secrets/pi-unraid-codex-lb`.
- The secret source itself must have restrictive host ownership/permissions readable by the configured non-root Pi UID/GID; local Compose does not apply Swarm-style secret uid/gid/mode controls.
- New `pi-unraid-provider` atomically initializes/preserves persistent `~/.pi/agent/models.json`:
  - provider `codex-lb`;
  - `api: openai-responses`;
  - Codex-LB `/v1` base URL;
  - literal environment reference `${CODEX_LB_API_KEY}`, never the resolved key;
  - default bootstrap model `gpt-5.6-sol`, configurable by `PI_CODEX_LB_MODEL`.
- Compatible existing `codex-lb` configuration and unrelated user provider/model content are preserved; conflicting/invalid existing configuration fails without replacing the user's file.
- The managed Pi launcher reads the dedicated secret and exports `CODEX_LB_API_KEY` only into the Pi child process.
- `pi-unraid-service health` remains the M02 runtime/service readiness signal.
- Separate `pi-unraid-service provider-health` checks provider shape, secret availability, Codex-LB health and authenticated `/v1/models`, with distinct non-secret diagnostics for missing/invalid credential, auth rejection and endpoint unreachability.
- No direct Pi ChatGPT/Codex OAuth fallback, pooled OAuth material, Codex-LB appdata mount/network join, Docker socket, host-root mount, inbound SSH or workstation dependency was introduced.
