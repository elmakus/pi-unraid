## Implemented foundation

- `compose.yaml` is the deployment source of truth.
- Exact accepted binds are declared:
  - `/mnt/user/appdata/pi-unraid/home -> /home/pi`
  - `/mnt/user/projects -> /projects`
  - `/mnt/user/pi-worktrees -> /worktrees`
- Bind declarations use `create_host_path: false`.
- Service policy is `restart: unless-stopped`, `TZ=Europe/Zurich`, and bounded `json-file` logs at 10 MiB x 3 files.
- The image carries a `pi` service account, `gosu`, and passwordless sudo for legitimate container-local administration.
- The entrypoint starts with bounded root authority only to validate/reconcile the configured `PI_UID`/`PI_GID`, then `exec`s the service command through `gosu pi`.
- UID changes temporarily point the passwd home at `/nonexistent` before `usermod --uid`, preventing `usermod` from recursively taking ownership of the mounted persistent home.
- The entrypoint changes ownership only of an empty `/home/pi` mount root. It never recursively `chown`s an existing home, `/projects`, or `/worktrees`.
- Existing-home permission mismatch fails with an actionable `pi-unraid init error` instead of taking ownership.
- `~/.pi/agent` scaffolding is created as the service user only after home permission checks pass.

## Corrective implementation detail found during execution

The first T02 build attempt at source head `8ddd187f64f0e3933b884769eebacffc05f443fa` failed before any container started because `usermod --move-home` returned exit code 12 when `/home/pi` already existed in the image.

This was a bounded L1 implementation defect. Commit `cd14a4bb43487fdccd4fb65f7df22f6ea01ebe59` removed the move-home operation, creates the image home explicitly, and keeps runtime UID changes protected from recursive bind ownership changes. The corrected source then passed all fixture and regression checks above.
