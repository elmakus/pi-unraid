### Must preserve

- Codex-LB is mandatory from the first real Pi model interaction; direct Pi ChatGPT/Codex OAuth is not a fallback or acceptance path.
- Codex-LB remains an independently deployed/persistent service. Pi must not mount, copy, restore or own Codex-LB appdata/OAuth material.
- Any Codex-LB source/deployment change must use Codex-LB's own accepted authority/workflow or an explicit operator-owned dependency procedure; this workstream must not silently edit another product.
- A dedicated Pi client credential is required. Its full value must not enter Git, images, normal logs or evidence.
- Pooled ChatGPT access/refresh tokens remain exclusively Codex-LB-owned.
- Multi-account routing is Codex-LB-owned; acceptance must preserve the documented continuation-state limitation.
- `chatgpt-ce-workstation` remains outside the dependency chain and receives no project-owned mutation.
- Existing Pi durable state and M01/M02 checkpoints are not rewritten to resolve a provider dependency.

### Must not / rationale that must travel

- Do not declare the current healthy-but-stale `0b673d...` deployment sufficient merely because `/health` is 200.
- Do not blindly fast-forward or redeploy Codex-LB without first recovering its own current authority/workflow and validating the intended current-enough baseline.
- Do not reuse an existing unrelated client key for Pi merely for convenience.
- Do not expose account identifiers, OAuth tokens, encryption keys or full client-key values in evidence.

## Outcome

The selected Codex-LB production dependency has a current-enough reviewed source/deployment baseline, is healthy and persistently owns usable ChatGPT/Codex account state, exposes the accepted authenticated Responses-compatible client surface, and has a dedicated Pi client credential plus a verified container-to-service reachability design ready for Pi integration.

## Scope

### Included

- Recover Codex-LB's own current project authority before any source/deployment mutation.
- Reconcile the fork/current image against the current upstream baseline and independently validate the resulting dependency under its own lifecycle.
- Verify deployed identity, health, persistence, eligible account capacity, proxy-key enforcement and accepted routing/sticky configuration without recording secret/account values.
- Create a dedicated Pi client credential only after explicit authorization; record only sanitized existence/metadata needed for acceptance.
- Establish and verify the intended Pi-container-to-Codex-LB network route without coupling Pi to workstation state or Codex-LB appdata.
- Produce immutable/sanitized prerequisite evidence that M03-T03/T04 can consume.

### Excluded

- Pi repository provider/config implementation.
- Production Pi deployment or creation of Pi appdata/worktree paths.
- Direct Pi OAuth.
- Workstation changes.
- Final Pi model-call/session/update/rollback/restart acceptance.

## Acceptance

1. Codex-LB source/deployment is reconciled to a reviewed, current-enough baseline under its own authority.
2. Exact accepted Codex-LB source/image/deployment identities are recorded without secrets.
3. Health and authenticated-client enforcement are verified, together with persistent OAuth/account-state ownership and usable account capacity.
4. Accepted routing/sticky behavior and continuation-state limitation are recorded accurately.
5. A dedicated Pi client credential exists through an approved non-Git path; no full key/token appears in repository evidence/logs/images.
6. The intended Pi→Codex-LB route is demonstrably reachable or has exact validated mechanics ready for disposable Pi integration.
7. Codex-LB remains independently persistent/deployed and `chatgpt-ce-workstation` remains unchanged.
8. No direct-Pi-OAuth bypass is introduced.
