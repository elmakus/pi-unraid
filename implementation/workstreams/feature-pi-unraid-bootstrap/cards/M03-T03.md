### Must preserve

- Use Pi's generic `openai-responses` compatibility seam to Codex-LB `/v1`; do not feed an opaque Codex-LB key into `openai-codex-responses`.
- Endpoint/client configuration must survive normal Pi restart/recreation through accepted persistent home/runtime secret handling.
- The dedicated client secret must not be committed, baked into an image or printed in diagnostics/evidence.
- Existing valid user Pi configuration must not be destructively overwritten by initialization.
- Pooled account OAuth tokens never enter Pi.
- Provider failure must remain distinguishable from Pi runtime/session/filesystem/Git health.
- M01/M02 non-root, mount, rollback, graceful-stop and logging guarantees remain intact.
- No Docker socket, host-root/unrelated-appdata mount, inbound SSH service or workstation dependency may be introduced.

## Dependencies

- M03-T02 terminal GREEN/accepted dependency result.

## Outcome

The repository contains the minimum reproducible Pi-side provider/secret/config integration for authenticated Codex-LB Responses access, with disposable verification proving idempotent persistence and safe failure/redaction behavior before any production Pi cutover.

## Scope

### Included

- Reconcile a focused OpenSpec contract JIT against current source and accepted M03-T02 dependency evidence.
- Add the minimum Compose/repository support for Codex-LB endpoint plus a runtime secret reference.
- Materialize/preserve compatible Pi provider/model configuration under the persistent native home without overwriting an already-valid configuration.
- Add deterministic health/diagnostic separation between Pi runtime readiness and model-access dependency failures.
- Add disposable tests for valid placeholder/test endpoint configuration where possible, missing/invalid credential, unavailable endpoint, repeated initialization and recreation/persistence.
- Regression-test inherited M01/M02 behavior.

### Excluded

- Real production client-key value in Git/test fixtures/evidence.
- Production Tower Pi path creation or deployment.
- Direct Pi OAuth.
- Codex-LB product/source changes.
- External Git/GitHub write acceptance or host/Docker restart.

## Acceptance

1. Repository/Compose can supply endpoint + secret by non-Git runtime mechanism without embedding the secret.
2. Persistent Pi provider/model configuration is compatible with `openai-responses` → Codex-LB `/v1` and survives recreation.
3. Initialization is idempotent and preserves an existing valid user configuration.
4. Missing/invalid secret and unavailable endpoint fail clearly without secret leakage or false durable-state-loss claims.
5. No pooled OAuth/token material is written into Pi.
6. Existing mount/security/non-root/runtime/update/graceful-stop/logging regressions remain GREEN.
7. OpenSpec and implementation agree on the provider/secret/persistent-config contract.

## Required tests / checks

- OpenSpec consistency/readback;
- Compose render with secret values redacted from captured evidence;
- disposable empty-home and populated-home initialization/recreation;
- missing/invalid secret and unreachable provider failure cases;
- source scan/log capture proving no literal secret is committed/emitted;
- existing M01/M02 verification suite portions affected by the change;
- exact image/source/runtime identities for the tested subject.

## External write/readback needs

Only repository changes and uniquely named disposable Docker/test resources are authorized by normal implementation scope. No Tower production Pi paths/service, real credential creation, Codex-LB production mutation, external Git write, or disruptive restart is included.
